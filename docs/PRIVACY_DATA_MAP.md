# Privacy data map

This is an implementation inventory, not a legal determination. It covers backend persistence, transient service data, and Android account data. Production database, object-storage, Redis, backup, and device-at-rest encryption settings are operational controls and must be verified for each deployment.

| Personal data / fields | Purpose | Where stored | Field-level encryption? | Retention | Deletion path |
|---|---|---|---|---|---|
| Email, date of birth, account status, auth version, password hash | Sign-in, age/consent routing, and account security | `users` relational row; email also used for account email workflows | Password is one-way hashed. Email and date of birth are not field-encrypted by the application | Until account deletion; password-reset rows expire and are cleaned hourly | `DELETE /api/v1/account`; user-row cascade |
| TOTP secret, factor type/status; recovery-code hashes | MFA authentication and recovery | `mfa_factors`, `mfa_recovery_codes` | TOTP secret is AES-GCM encrypted; recovery codes are one-way hashed | Until factor/account deletion or code replacement | MFA/account deletion cascade |
| MFA attempt timestamp, outcome, and source IP | Abuse detection and rate limiting | `mfa_attempts`; failed-attempt rate-limit key in Redis | No field-level encryption | Database rows cascade with account; Redis rate limits expire by configured window and account deletion removes the user's hashed key | Account deletion; configured rate-limit expiry |
| Guardian email, consent status, token hash/expiry, resend metadata, approved IP, verification timestamp | Obtain and record guardian consent for under-13 accounts | `guardian_consents`; consent links are sent by configured email service | Consent token is hashed; email and IP are not field-encrypted | Until account deletion. On deletion, a separate minimal evidence record may remain (see below) | Account deletion removes the raw consent row and token |
| **Guardian-consent evidence:** SHA-256 user-ID hash, consent status, verified timestamp, optional expiry | Preserve minimal consent evidence for the configured retention period | `guardian_consent_evidence` | Hash is pseudonymous, not anonymous; other columns are not field-encrypted | `GUARDIAN_CONSENT_EVIDENCE_RETENTION_DAYS` defaults to `0` (no expiry) until a legally reviewed value is configured | Expired rows are removed by the hourly retention worker; no-expiry rows require an approved retention decision and manual policy/configuration change |

Legacy shared cache keys created before profile-scoped keys expire by their configured TTL |

| Notification preferences, quiet hours, timezone | Schedule reminders according to preferences | `notification_preferences`; Android local preferences/Room | No field-level encryption | Until account deletion | Account cascade and local account-data wipe |
| Password-reset token hash and expiry | Password recovery | `password_reset_tokens` | Token is one-way hashed | Until use/expiry; expired rows are removed by the hourly retention worker in batches of 100 | Reset flow, expiry cleanup, or account cascade |
| Account-deletion job user/profile IDs and image-path manifest | Resume deletion after external cleanup fails | `account_deletion_jobs` | Not field-encrypted; transient operational record | Only while deletion is pending; removed after finalization | Resumable deletion worker; protect this table and its backups as sensitive |
| Deletion audit hash and timestamp | Record that a deletion completed without retaining personal content | `account_deletion_audit` | User ID is SHA-256 hashed; timestamp is retained | No automatic expiry is currently configured | Retained by design; change requires an approved audit-retention policy |
| Redis account/profile caches, per-profile AI cache, quota/rate-limit/idempotency data | Caching, abuse prevention, request replay control | Redis | AI keys use a profile-scoped namespace; response data is not field-encrypted | Per-key configured TTL; retention worker removes persistent legacy rate-limit/idempotency keys | Account deletion scans and removes matching user/profile keys; stateless JWTs are invalidated by auth-version increment and user removal |
| Access/refresh tokens and user ID | Maintain Android session | Android `EncryptedSharedPreferences` backed by Android Keystore | AES-256-GCM values and AES-256-SIV preference keys | Until logout/account deletion | Logout clears secure storage; deletion also clears it as part of local account cleanup |
| Synced questions, answers, quizzes, attempts, bookmarks, sync metadata, notification work | Offline study and scheduled local reminders | App-private Room database, preferences, WorkManager | Room records are not field-encrypted by the app; storage protection depends on the device/OS | Until local logout/account cleanup or app removal | Account deletion clears Room, account-scoped preferences and WorkManager jobs, image cache, and FCM token |
| Request/operational metadata (correlation ID, route, status, timing, provider/model, token counts, outcome) | Diagnostics, abuse monitoring, and AI cost tracking | Application logs and AI usage records | No field-level encryption; application logs are configured not to include question text or raw identifiers in the reviewed paths | Operational logging retention is deployment-managed and must be configured | Log-platform retention/deletion policy; personal content should not be written to logs |

## Data minimization and security notes

- Migration V14 removes the redundant `preferred_subject` column and unused `answers.raw_content` column. The profile API no longer accepts or returns `preferredSubject`; subject values remain attached to questions rather than persisted as profile preferences.
- Analytics and crash-reporting SDK instrumentation is disabled/removed in the Android app. No analytics event stream is part of the current data inventory.
- AES-GCM currently applies to the server-side TOTP secret, not to question, answer, quiz, or profile fields. Android session-token values use encrypted shared preferences. Do not interpret these controls as application-level encryption of the database or backups.
- Server encryption keys come from environment configuration (`MFA_ENCRYPTION_KEY`); do not store the key in source control. The local development validator requires 32 UTF-8 bytes; the AES utility accepts valid AES key sizes (16, 24, or 32 bytes). Existing production keys must be validated before rollout.
- Key rotation procedure: deploy a versioned key identifier and dual-key decryption support before changing the active key; decrypt/re-encrypt each stored TOTP secret with the new key in a controlled migration; verify MFA for a test cohort; then remove the old key only after confirming no ciphertext depends on it. The current implementation does **not** provide key versioning or automated rotation; this procedure is a deployment prerequisite, not a feature already delivered.
- TLS: Android release builds reject a non-HTTPS `API_BASE_URL`, and the main network security config disallows cleartext. Debug configuration permits HTTP only for emulator/loopback hosts. Local development is HTTP-only; production must use HTTPS.
- No application field-level encryption for the designated learning-content fields is present. If ADD-06 intended a broader sensitive-field scope, that scope still needs implementation and review.
